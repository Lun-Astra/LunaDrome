### Vision clarified
- Luna runs a self-hosted **Navidrome** server for his music library, plus a self-hosted **music downloader** (to be integrated later), and **Bluetooth speakers connected via SendSpin** (to be integrated later).
- Goal: a personal media player in the spirit of **Finamp** / **Ensemble** (Jellyfin-style clients), but for Navidrome.
- First milestone (v0): Windows desktop app with a Navidrome login screen, browse artists/albums/songs, and basic playback. SendSpin and downloader integration are explicitly deferred.

### Stack decision
- Only **.NET 6 SDK** is installed on this machine (no .NET 8+), so the app targets **net6.0-windows** with **WPF**. Revisit upgrading the SDK later if we want newer .NET features.
- Navidrome speaks the **Subsonic API**. Auth uses the token scheme: `token = md5(password + salt)`, sent as `u`, `t`, `s`, `v`, `c`, `f=json` query params — implemented in `NavidromeClient.BuildUrl`.
- Password is **never persisted to disk** — `SettingsService` only remembers server URL + username for convenience on next login (stored in `%AppData%\Musicplayer\settings.json`).
- Playback uses WPF's `MediaElement` pointed directly at the Subsonic `stream.view` URL (works for standard codecs via Windows Media Foundation). No local caching/download yet.

### Secure password persistence + navigation rework (Home / Artists / Albums / Songs)
- Feedback: queue toggle button "didn't work" (code looked correct on inspection — most likely Luna was testing a stale running instance from before the fix, since a prior `dotnet build` had failed with a file lock from an old `dotnet run` process still holding the .exe open). Stored as base64 in `settings.json` alongside server URL/username, only when "Remember me" is checked (unchecking it clears all saved settings, including previously-saved password).
- `LoginWindow` now attempts **auto-login** on startup if a saved+decryptable password exists: pre-fills the password field and immediately tries signing in (status shows "Signing you in..."), falling back to the normal manual form if it fails (e.g. password changed server-side, or settings copied to another machine/user where DPAPI can't decrypt it).
- **Navigation rework**: `MainWindow` now has a left sidebar (`RadioButton`s styled via new `NavItemStyle` in `App.xaml` — same left-accent-bar look as list selection) switching between four overlapping "page" containers in one Grid cell: `HomePage` (recently-added album grid, `getAlbumList2` type=`newest`), `ArtistsPage` (the original Artist→Album→Song drill-down, unchanged), `AlbumsPage` (every album in the library, `getAlbumList2` type=`alphabeticalByName`, size 500), `SongsPage` (every song in the library). - **"All songs" endpoint**: implemented via Subsonic `search3.view` with an **empty query string** (`GetAllSongsAsync` in `NavidromeClient`) — Navidrome is expected to treat empty query as "match everything", capped at 500 results. **This is unverified against Luna's actual server** — if the Songs page comes back empty or errors, the fallback is to iterate `getAlbumList2` pages and call `getAlbum` per album instead (slower but guaranteed to work). Flagged as the top thing to check first if "All Songs" looks wrong.
- Shared resources moved into `MainWindow.xaml`'s own `Window.Resources` (not `App.xaml`) — `AlbumCardTemplate` (album cover art card, reused by Home/Artists/Albums pages) and two `ContextMenu`s (`AlbumSongContextMenu` with "Add album to queue", `LibrarySongContextMenu` without it, since the library-wide Songs page has no single "current album"). This repeats the earlier `EventSetter`-scope lesson: since these menus' `Click` handlers live in `MainWindow.xaml.cs`, the resources must be declared in `MainWindow.xaml`, not `App.xaml`.
- Because the two song `ContextMenu`s are both wired to the *same* handler methods (`PlayNowMenuItem_Click` etc.), those handlers now resolve the actual source `ListView` via `((MenuItem)sender).Parent as ContextMenu` → `.PlacementTarget as ListView`, instead of hardcoding a control name — a `GetOwningListView` helper. This lets one set of menu handlers serve both the per-album Songs list and the whole-library Songs list.
- **Same XAML-init-order bug as the volume-slider crash, avoided proactively this time**: `NavHome`'s `IsChecked="True"` was *not* set in XAML (that would fire `Nav_Checked` mid-`InitializeComponent()`, before `_client` and later-declared elements like `HomeAlbumsList` exist). Instead it's set from code (`NavHome.IsChecked = true;`) as the last line of the `MainWindow` constructor, after every field and `ItemsSource` is wired up. **General rule reinforced: any XAML-declared initial state (`IsChecked`, `Value`, `IsSelected`...) that has a code-behind handler must either be set from code after `InitializeComponent()`, or the handler must null-guard against elements/fields declared later in the same constructor.**

Reusing the *content* of the original tab implementation (page DockPanel, sort/search bar, context menus, all the backend calls) made the rework fast even though the shell around it changed a lot.
- Track view (art+title+artist column, Sort ▾ popout, ascending/descending toggle, search box) matches Artists/Tracks pages, same as before. `+` button next to the `PLAYLISTS` sidebar header creates an empty playlist via a reusable `Views/InputDialog` (simple modal text-input window — WPF has no built-in InputBox). Right-click a playlist in the sidebar for "Delete playlist" (falls back to Home if the deleted one was the page being shown); right-click a track inside one for "Remove from playlist" alongside the usual Play now/Play next/Add to queue.
- **"Add to playlist" submenu** added to every song context menu in the app (per-album Tracks, library-wide Tracks, the new Playlist track view, and the Queue) via a shared `AddToPlaylistSubmenu_SubmenuOpened` handler: it re-fetches the playlist list fresh each time the submenu opens (so it's never stale) and populates it with "New playlist..." plus one entry per existing playlist. ### Visualizer styling: "take it from Feishin 1:1" — hit a real technical wall
- Investigated what "1:1" would actually mean: Feishin's default visualizer isn't its own code, it's the third-party **audioMotion-analyzer** JS library (Web Audio API + Canvas, dozens of config options - mode, gradient, radial, LED bars, etc.), used as an npm dependency. There's no .NET/WPF equivalent and no realistic way to port it - flagged this to Luna directly rather than either refusing or silently faking a port. He chose the pragmatic middle ground: approximate audioMotion-analyzer's well-known **default** appearance instead of a true port.
- Implemented that default look: a green→yellow→red "classic" gradient per bar (green at low levels, only reaching red when a band is genuinely loud) plus falling peak markers (VU-meter "gravity" behavior - snap up instantly, decay slowly).
- **How the gradient effect actually works** (this is the standard technique for "short bar = green, tall bar reaches red", not something obvious from a naive per-bar-height gradient): each band is a `Grid` "column" containing three overlapping children - (1) a `Border` filled with a single shared, **frozen** `LinearGradientBrush` sized to the column's *full* height and never resized, so its green/yellow/red stops always land at the same absolute pixel positions; (2) a `Border` **mask** painted in the app's background color, anchored to the top, whose `Height` is set each frame to `containerHeight - barHeight` - it covers everything above the current bar height, revealing only the bottom slice of the shared gradient (always green for quiet bars, reaching further up into yellow/red only when the band is loud); (3) a thin white peak-marker `Border` positioned via `Margin` from the bottom. A naive per-bar gradient (resizing the gradient's own bounding box to match each bar's height) would make every bar - loud or quiet - always fade to red at its own top, which is wrong.
- Peak decay: `_visualizerPeakHeights[i]` snaps up to the new bar height instantly if it's higher, otherwise falls by a fixed 4px per spectrum frame (~20fps) - simple linear "gravity," not physically modeled, but reads correctly.

### Visualizer bug: "only shows 1 bar" — real bug, fixed
- Root cause: `ComputeBands` split the spectrum into 32 **equal-width (linear)** frequency bands. Music energy is overwhelmingly concentrated below ~1kHz, so with linear splitting almost all of it landed in band 0 (bass) while every other band - each covering a much wider, energy-sparse slice of the spectrum - sat near-silent. Looked like exactly one bar moving.
- Fixed by splitting bands on a **log frequency scale** instead (40Hz to min(16kHz, Nyquist), log-spaced edges converted to FFT bin ranges) - the standard approach real spectrum analyzers (and audioMotion-analyzer) use. Needed the actual sample rate threaded through from `WaveFormat.SampleRate` (previously `ComputeBands` was a pure function of the FFT buffer alone, unaware of sample rate, which is only valid for the linear/uniform-bin-width scheme it's replacing).

### Visualizer restyled again: single bending line instead of bars

  1. **Frame-to-frame exponential smoothing** per band (`_visualizerSmoothed[i] = smoothed*0.55 + new*0.45`) - a connected line makes raw per-frame FFT jitter far more visually obvious than independent bars ever did, since bars can each jump around independently without looking "wrong," but a single line snapping around looks broken.

### Visualizer still laggy after the first perf pass — real architectural fix
- Luna: "no, still laggy" after the FftLength/allocation fixes above. Investigated further via **reflection on the actual installed NAudio.Wasapi.dll** (`Add-Type` + `GetConstructors()`) rather than guessing: `WasapiLoopbackCapture` only publicly exposes `()` and `(MMDevice)` constructors. Its base class `NAudio.CoreAudioApi.WasapiCapture` *does* have a `(MMDevice, bool useEventSync, int audioBufferMillisecondsLength)` constructor for configuring buffer size, but `WasapiLoopbackCapture` doesn't forward it - so there's no supported way to ask it for a smaller buffer than its ~100ms default. That default is almost certainly the real remaining cause: audio arrives in ~100ms bursts (each containing several of our 1024-sample FFT windows fired back-to-back), not a steady stream - "43fps" on paper, but visually stutter-then-jump-then-stutter.
- **Fix: decouple rendering from audio delivery entirely**, rather than continuing to fight WASAPI's buffering. `AudioVisualizer` no longer raises a `SpectrumReady` event; it exposes a thread-safe pull instead - `CopyLatestBandsTo(float[])`, protected by a plain `lock`, always returning whatever the capture thread most recently computed. The UI side now hooks `CompositionTarget.Rendering` (fires once per actual display frame, ~60fps, independent of audio timing) via `OnVisualizerRenderFrame`, which pulls the latest bands, exponentially smooths toward them (weight bumped to 0.7 old/0.3 new now that rendering is much faster than the audio updates it's smoothing between), and redraws the curve. `UpdateVisualizerCaptureState` now hooks/unhooks `CompositionTarget.Rendering` in lockstep with starting/stopping the WASAPI capture (guarded by a new `_visualizerRenderHooked` bool so it doesn't double-subscribe), so nothing renders when the panel isn't visible or nothing's playing.
- This is the standard architecture for real-time audio visualizers in general (never couple UI frame rate to audio buffer callback timing) - worth remembering if the same lagginess symptom ever shows up elsewhere in this app.

### Visualizer left-edge clipping / off-center — WPF Shape auto-centering gotcha
- "yes its faster, but clipping left in the wall.. like its not centered." Two compounding causes:
  1. **WPF `Shape` auto-centering**: a `Path` (a `Shape`) with the default `Stretch="None"` sizes itself to its geometry's bounding box during layout, and if that computed box is smaller than the space its parent `Grid` actually gives it, WPF **centers** the rendered geometry within that leftover space rather than anchoring it at the origin the app computed - shifting everything and making the mismatch look like clipping on one side. Fixed with explicit `HorizontalAlignment="Left" VerticalAlignment="Top"` on `VisualizerPath`, so it always anchors at (0,0) in `VisualizerContainer`'s own coordinate space, matching the coordinates `OnVisualizerRenderFrame` actually computes.
  2. Same edge-inset issue the vertical padding already fixed, just never applied horizontally: the leftmost/rightmost points sat exactly at `x=0`/`x=width`, so the round line-caps at those endpoints rendered half outside the container. Added a matching horizontal `padding` (same 6px constant), computing `x` within `[padding, width - padding]` instead of `[0, width]` - mirrors the existing vertical `drawableHeight` treatment.

### Visualizer kink saga — resolved (or at least redirected) once an actual screenshot arrived
- After 5+ blind fix attempts from text descriptions alone (see below for that history), Luna uploaded `src/Musicplayer.App/example.png` (a screenshot, saved directly into the project folder - worth checking there first if this ever recurs). Text descriptions of "hard cut," "straight line up," "still there" all pointed plausibly at the boundary-tangent-continuity theory and were each partially-plausible-sounding, but the actual shape of the problem (spiky everywhere, not just at one seam) was only obvious once actually visible.

### Visualizer: the actual kink was a genuine tangent-formula mismatch, not an illusion
- "the line is straight at the solid point yes, but instead of a nice bending / flowing line its getting a hard cut up." This was more specific feedback than the earlier "still there" reports and pointed at a real, findable bug rather than another geometric guess: the connector segment (index 1, A1→R0) computed R0's *incoming* tangent using its real left neighbor, `R0 - (R1-A1)/6`. But the very next segment (the first interior segment, index 2, R0→R1) computed R0's *outgoing* tangent by duplicating R0 itself as its own "previous point" (leftover from when the band-point chain had no real neighbor outside its own bounds) - `R0 + (R1-R0)/6`. Two different formulas for the tangent at the exact same point is a genuine mathematical C1-discontinuity, not a rendering artifact or an illusion of a short connector - it produces an actual corner.
- Fixed by simplifying the interior segments' neighbor lookup: since the points array now has *real* points at exactly `points[i-1]`/`points[i+2]` for every interior segment (A1 at the left boundary, B0 at the right - they exist precisely because of the anchor-zone redesign), the `i == 2` / `i == bandCount` duplicate-boundary special cases were unnecessary leftovers and actively wrong. Removed them; interior segments now always reference the true neighbors, which are the exact same points the connector segments already use - guaranteeing the tangent at R0 (and at R_last) is computed identically by both segments that meet there.
- Fade-in/out window (previous entry) is still in place and still valid - it solves a different problem (not enough horizontal room for a large value swing), independent of this tangent-formula bug.

### Visualizer: fade-in/out window, not more curve-fitting tricks
- "the straight line up is less but still there." Recognized this wasn't fixable with more tangent/control-point tuning: the connector zone is only ~38px wide, and bass can swing from silent to near-max - cramming that much vertical change into that little horizontal space will look like a steep, near-straight line **no matter how the curve math is tuned**, since there's genuinely not enough room for a visible bend.
- Fixed the actual cause instead of the symptom: fade the first/last **6 bands'** amplitude in/out linearly (`fade = (i+1)/(fadeBands+1)` ramping 0→1, mirrored at the other end), multiplying each of those bands' Y-displacement-from-baseline by its fade factor before building the curve. This spreads the same rise across ~6 band-widths of real horizontal space in the moving zone, instead of forcing all of it through the narrow connector - so by the time the curve reaches the connector, the value it's transitioning to is already small and the connector's job is easy.
- **General lesson**: after 3 rounds of adjusting Bezier control-point/tangent math for this same "line up" symptom with only partial improvement each time, the actual fix was to change what data feeds the curve (fade the input values), not the curve-fitting math itself - worth remembering when a curve *keeps* looking wrong after several purely-geometric tuning attempts: check whether the underlying data has a hard discontinuity the geometry can't be reasonably expected to smooth over.

### Visualizer: connector segments needed to be curves with a forced horizontal tangent, not lines
- "almost, between the static zone instead of the curve there is a straight line up" - the LineSegment connector fix (previous entry) traded the "bleeding curve" bug for a new, more visible one: a dead-straight diagonal line right where the flat zone meets the data, an obvious kink.
- Final shape: the two flat segments (index 0 and the last) stay `LineSegment`s (still genuinely flat, unchanged). The two **connector** segments (index 1 and `bandCount+1`) go back to being `BezierSegment`s, but with one control point deliberately pinned to the *same Y* as the flat zone's endpoint - e.g. for the entry connector, `Point1 = (p1.X + (p2.X-p1.X)/3, p1.Y)` (note: `p1.Y`, not a Catmull-Rom-derived Y). Forcing that control point's Y to match the flat line's Y makes the curve's initial tangent exactly horizontal, so it leaves the flat `LineSegment` with a matching direction (no visible corner) and only starts actually bending a short distance in - solving both the "kink" and the "premature bend" problems at once. The connector's *other* control point still leans on the next real band point (interior chain) for a smooth handoff, same idea as the original Catmull-Rom math. The exit connector mirrors this arriving at the second flat zone.
- This turned out to be a genuinely fiddly problem across four attempts (fixed points → LineSegment anchors → this) precisely because "flat, then curves, with no visible seam either way" has three simultaneous constraints (no premature bend, no overshoot, no hard corner) that a single uniform segment-generation strategy can't satisfy - it needed three distinct segment treatments (line / tangent-pinned Bezier / free Bezier) for the three zones.

### Visualizer: anchor zones needed to be real LineSegments, not Bezier
- "no.. the archorzone isnt fully visible" - the fixed-baseline-point approach from the previous fix wasn't enough: a smooth spline's tangent calculation blends a curve's bend into its *neighboring* segments too, so even with a static anchor point at each end, the Bezier segment leading up to it was already curving away from flat before actually reaching it - the flat zone looked shorter than the real 38px because it effectively was.
- Fixed by making the anchor zones (and the short "connector" segments joining them to the real data) genuine `LineSegment`s instead of `BezierSegment`s. `UpdateSmoothCurve` now builds a **mixed** `PathSegment` chain: segments 0/1 and the last two are `LineSegment`s (flat-start→flat-end, and flat-end→first-real-point / last-real-point→flat-start), everything in between is the original Catmull-Rom `BezierSegment` chain - now built using **only the band-point sub-list**, with its own independent boundary duplication (never referencing the anchor/connector points at all). A `LineSegment` between two points at the same Y is mathematically incapable of curving, so the flat zone is now flat for its *entire* declared width, no exceptions, and the connector segments (straight lines with zero control points) can't overshoot either.
- The `IsFlatOrConnector(segmentIndex)` check (`segIndex is 0 or 1 || segIndex >= segmentCount - 2`) picks which of the 3 pre-created segment types to build once at initialization; per-frame updates just set `LineSegment.Point` or `BezierSegment.Point1/2/3` depending on which type is at that index, keeping the existing "mutate persistent segments in place" perf optimization intact.

### Visualizer: the real bug was Bezier overshoot, not layout - fixed via anchor zones (partially superseded by the LineSegment fix above, kept for the overshoot-diagnosis narrative)

### Visualizer perf + clipping fixes (superseded by the render-decoupling fix above, kept for the padding/allocation notes which still apply)
- "very low fps, also clipped in the bottom." Two independent causes for the fps complaint:
  1. `FftLength` was 2048, which at a typical 44.1kHz capture rate only fires `SpectrumReady` ~21 times/sec. Halved to **1024** (~43fps) - frequency resolution loss is irrelevant since only 32 log-spaced bands get read out of it anyway.

- **Bottom (and top) clipping**: the curve's Y mapped 0..1 straight to the container's full pixel height, so a silent reading sat with its stroke centered exactly on the bottom edge - half the line's `StrokeThickness` rendered outside the visible area. Added a fixed 6px `padding` top and bottom (`drawableHeight = height - padding*2`), so both extremes now render fully inside the container.

- **Second bug, found right after: `NowPlayingText` (bottom-left song title) turned plain black.** Cause: setting an explicit `Style="{StaticResource ClickableTextStyle}"` on an element **replaces** implicit style resolution entirely, not merges with it - so any `TextBlock` relying on the app's implicit base `Style TargetType="TextBlock"` (which sets `Foreground="{StaticResource TextPrimaryBrush}"`) for its default color, rather than setting `Foreground` explicitly on itself, silently lost that default and fell back to WPF's stock black once it got an explicit keyed `Style`. `NowPlayingText` was the one clickable text with no explicit `Foreground` of its own (every other one already had `Foreground="{StaticResource TextSecondaryBrush}"` or similar set directly, which - being a local value - wins over anything a `Style` sets regardless, so they were unaffected). Fixed by adding `BasedOn="{StaticResource {x:Type TextBlock}}"` to `ClickableTextStyle` so it inherits the base style's `Foreground`/`FontFamily` instead of discarding them.
- **General lesson for this codebase, worth checking any time a new `x:Key`'d `Style` gets applied to a `TextBlock`/`Control` that previously relied only on an implicit type-wide style**: an explicit keyed `Style` on an element always fully replaces implicit style resolution rather than layering on top of it - give the keyed style `BasedOn="{StaticResource {x:Type T}}"` whenever the element being styled might depend on the base style's own setters (this app's implicit `TextBlock`/`Button`/`Window` styles all set `Foreground`/`FontFamily` defaults that are easy to silently lose this way).

### Uno visualizer "very slow and low fps" — fixed 2026-09-24
- Two separate causes, found by measuring (temporary fps counter + process CPU time), not guessing:

### v3.6.5: no scroll hitch every 10s while playing — 2026-09-30
- Luna: scrolling "sometimes" lags. Cause found: `ProgressTimer_Tick` calls `SaveQueueState()` every 25 ticks (~10s) while playing, and it serialized the whole queue + preferences to JSON and wrote both files on the UI thread. Measured with a 5000-song queue: 48 ms per save on the calling thread (about 3 dropped frames); now 3 ms.
- `StateFileWriter` (Core) writes a file now or in the background (write-then-rename). Per file, the newest save wins: each save takes a sequence number, and an older background save that finishes late is dropped. The periodic tick uses `SaveQueueState(background: true)`: the song clones and prefs JSON are made on the UI thread, then serialize + write run off it. Exit / sign-out / update keep the synchronous save.
- Not verified in Luna's running app yet. If scrolling still hitches, the older maximized-Home frame cost (~57 ms/frame, see the 2026-09-24 investigation) is the next suspect.

### #28 part 1: streaming quality (dev, not released) — 2026-10-03
- Settings > Playback "Streaming quality" chips (built in BuildSettingsChoices like the theme chips; a ComboBox's open list stayed white on this Uno theme, so no ComboBox): Original (as is), Very high (MP3 320), High / Normal / Low (Opus 160 / 96 / 24). `Preferences.StreamQuality` → `NavidromeClient.StreamQuality`; `GetStreamUrl` adds `format` + `maxBitRate`. Navidrome caches conversions, so later requests are exact.
